# ข้อจำกัดและความต่างจาก QB64

[สารบัญคู่มือ](../README.md) · [English](../en/limitations.md)

QBNex คอมไพล์ BASIC เป็น QIR แล้วรันด้วย runner ภาษา Rust ชื่อ `qb-exec`
ไม่มีคอมไพเลอร์ C หรือ C++ อยู่ในขั้นตอนใดเลย หน้านี้บอกว่าข้อนี้มีผลอะไร
กับโปรแกรมที่เขียนไว้สำหรับ QB64 และรวบรวมข้อบกพร่องที่ยังไม่ได้แก้ ทุกข้อ
ตรวจกับโค้ดแล้ว ข้อที่แก้แล้วไม่ได้ใส่ไว้ ส่วนการเปลี่ยนแปลงที่ตั้งใจและบั๊ก
ของ QB64 ที่แก้แล้วดูที่[ความแตกต่างจาก QB64 และ QBasic](differences.md)

## การ build QBNex และการ build โปรแกรม

- **การ build QBNex ต้องมี Rust toolchain** `scripts/setup_win.cmd` (รวมถึง
  `setup_lnx.sh` และ `setup_osx.command`) ใช้ `cargo` build runner ถ้าไม่มี
  จะหยุดพร้อมข้อความ "cargo was not found" ถ้าตั้ง `QBNEX_QB_EXEC` เป็น
  `qb-exec` ที่ build ไว้แล้ว จะข้ามขั้นนี้ไป ไม่ต้องใช้ MinGW หรือคอมไพเลอร์ C ใด ๆ
- **การ build โปรแกรม BASIC ไม่ต้องใช้อะไรเพิ่ม** QBNex ที่ build แล้ว (หรือชุด
  release) คอมไพล์โปรแกรมได้โดยไม่ต้องติดตั้ง Rust คอมไพเลอร์จะคัดลอก runner
  ที่ build ไว้จาก `crates/engine/exec/bin/<os>/` แล้วต่อโปรแกรมเข้าไปท้ายไฟล์
- `qb fmt`, `qb lsp` และ `qb dap` ต้อง build เครื่องมือของมันด้วย `cargo` ก่อน

## ไฟล์ปฏิบัติการสองแบบ

| แบบ | คืออะไร | สถานะ |
| --- | --- | --- |
| Runner + QIR (ค่าเริ่มต้น) | สำเนาของ `qb-exec` ที่ต่อ QIR ของโปรแกรมไว้ท้ายไฟล์ ตอนเริ่มจะรันโปรแกรมบน VM และคอมไพล์โค้ดที่ทำงานบ่อยด้วย Cranelift (JIT) | ใช้ได้แล้ว |
| Native | `qb-exec build` นำ machine code ที่สร้างไว้ล่วงหน้ามา link เป็นไฟล์ปฏิบัติการด้วย `rust-lld` คอมไพเลอร์จะทำแบบนี้ก็ต่อเมื่อมี native kit อยู่ใน `crates/engine/exec/bin/<os>/native/` | ทดลอง |

ไฟล์แบบ native:

- native kit ต้อง build ด้วย Rust toolchain (`scripts/native-kit.ps1` /
  `native-kit.sh`) ทั้งสคริปต์ setup และชุด release ไม่ได้ build ให้ ถ้าไม่มี kit
  หรือ link ไม่สำเร็จ คอมไพเลอร์จะสร้างแบบค่าเริ่มต้นแทน
- เป็นโปรแกรม console เท่านั้น โปรแกรมที่มีหน้าต่างยังใช้แบบ runner + QIR
- ยังมี VM และ Cranelift อยู่ข้างใน machine code ใช้ชุดคำสั่งเสริมของ CPU
  เครื่องที่ build
- ทดสอบบน Windows ในเครื่องพัฒนาแล้ว ส่วน Linux (ELF) และ macOS (Mach-O)
  build และทดสอบใน CI เท่านั้น

ทั้งสองแบบมีขนาดและความเร็วพอ ๆ กัน โปรแกรม hello world ใหญ่ประมาณ 8.5 MB
และเริ่มทำงานในราว 48 ms

## DECLARE LIBRARY

runner เรียกฟังก์ชันเป็น machine code โดยตรงผ่าน `crates/engine/ffi`
(calling convention แบบ Win64, SysV x86-64 และ AArch64) เมื่อไม่มีคอมไพเลอร์ C:

- **ใช้ source หรือ header ของ C และ C++ ไม่ได้** QB64 คอมไพล์ header
  (`name.h`) หรือ source C/C++ ที่อยู่คู่กับ `DECLARE LIBRARY "name"` เข้าไปใน
  โปรแกรม แต่ QBNex ทำแบบนั้นไม่ได้
- **ใช้ static library ไม่ได้** (`.a`, `.lib`, `.o`) เพราะไม่มีขั้นตอน link
- **shared library ถูกโหลดตามชื่อ** `DECLARE LIBRARY "name"` และ
  `DECLARE DYNAMIC LIBRARY "name"` จะโหลด shared library ตอนเรียกฟังก์ชันของมัน
  ครั้งแรก (ทั้งใน VM, JIT และ `.exe` แบบ native) โดยค้นหาชื่อแบบเดียวกับ QB64:
  - Windows: `name.dll` ตาม path ที่ให้ไว้ในชื่อ, ใน `System32` แล้วจึงตาม
    DLL search path ปกติ
  - Linux: `libname.so` (หรือ `libname.so.version` เมื่อเขียน `"name:version"`)
    ตาม path, ใน `/usr/lib64` และ `/usr/lib`
  - macOS: `libname.dylib` แบบเดียวกัน

  บน Windows คอมไพเลอร์จะหยุดด้วย `LIBRARY not found` ถ้าไม่มี `.dll` นั้น
  ส่วนบน Linux และ macOS ถ้าไม่มีไลบรารีจะเกิด error 453 ตอนเรียกครั้งแรก
- **ฟังก์ชันถูกค้นหาจากที่ไหน** ฟังก์ชันที่ประกาศไว้จะถูกค้นตามลำดับนี้: ใน runner
  (ฟังก์ชัน `ext.*` ของไลบรารีมาตรฐาน), ในไลบรารีที่ระบุในบล็อก `DECLARE LIBRARY`
  ของมัน, ในตัวโปรแกรมเอง, แล้วจึงในไลบรารีของระบบ:
  - Windows: ucrtbase, msvcrt, kernel32, user32, gdi32, advapi32, shell32,
    ole32, oleaut32, comdlg32, winmm, ws2_32 และ ntdll
  - Linux: libc, libm, libdl และ libpthread
  - macOS: libSystem

  ถ้าหาฟังก์ชันไม่เจอ จะเกิด error 453 ตอนเรียกครั้งแรก
- **ชนิดข้อมูล** ใช้ได้กับจำนวนเต็มทุกขนาด, SINGLE, DOUBLE, `_OFFSET`, สตริง
  (ส่งเป็น pointer ไปยังไบต์ของสตริง) และอาร์กิวเมนต์แบบ BYREF (ส่งเป็นที่อยู่)
  ที่ยังไม่รองรับคือ `_FLOAT` ทั้งในอาร์กิวเมนต์และค่าที่คืน (D-112), ฟังก์ชัน C
  ที่รับอาร์กิวเมนต์จำนวนไม่คงที่ และ callback จาก C กลับมาที่ BASIC

## CALL ABSOLUTE

`CALL ABSOLUTE` รัน machine code ในตัวจำลอง x86 แบบ 16 บิตโหมด real mode
ขนาดเล็ก แบบเดียวกับ runtime ของ QB64 รองรับคำสั่งที่ routine ของ QBasic
ทั่วไปใช้ส่งค่า ได้แก่ MOV, PUSH, POP, prefix ของ segment, prefix ของ operand
และ address แบบ 32 บิต, `INT` และ RETF คำสั่งอื่น (เลขคณิต, เปรียบเทียบ,
กระโดด, วนลูป, คำสั่งสตริง) จะหยุดด้วย error 86

ตอบสนองเฉพาะ `INT 33h` (เมาส์) ฟังก์ชัน 0 (reset) และ 3 (ตำแหน่งและปุ่ม)
interrupt อื่นเช่น `INT 21h` และ `INT 10h` ไม่ทำอะไร และไม่รองรับ
`CALL INTERRUPTX`

## PEEK, POKE และ DEF SEG

conventional memory มีขนาด 1 MB บวก 64 KB พื้นที่ต่อไปนี้ทำงานเหมือนบน PC:

| ที่อยู่ | เนื้อหา |
| --- | --- |
| `&H417`, `&H418`, `&H496` | สถานะปุ่ม shift ของคีย์บอร์ด |
| `&H41A`, `&H41C`, `&H41E`... | buffer ของคีย์บอร์ด (head, tail, ปุ่ม) |
| `&HA0000` | พิกเซลของ SCREEN 13 (320x200) |
| `&HB8000` | หน้าข้อความของ SCREEN 0 (ตัวอักษร, attribute) |

ไม่ได้จำลอง: ไบต์โหมดวิดีโอ `&H449` และตัวนับ timer ที่ `&H46C` ไบต์อื่นของ BIOS
อ่านได้ 0 ถ้าโปรแกรมไม่ได้ POKE ไว้

ตัวแปร BASIC ไม่ได้อยู่ใน conventional memory `VARPTR` จะคัดลอกตัวแปรไปไว้ที่นั่น
การ POKE ลงสำเนานั้นเปลี่ยนสมาชิกของ array ได้ แต่ไม่เปลี่ยนตัวแปรเดี่ยว

## INP, OUT และ WAIT

| พอร์ต | INP | OUT |
| --- | --- | --- |
| `&H3C7` | - | ตำแหน่งอ่านของ DAC |
| `&H3C8` | - | ตำแหน่งเขียนของ DAC |
| `&H3C9` | ค่าสี R, G, B ของ palette ที่ตำแหน่งอ่าน | ค่าสี R, G, B ของ palette (ค่า 6 บิต) |
| `&H3DA` | บิต 3 ตั้งหนึ่งครั้งต่อเฟรม 60 Hz (retrace) | - |
| `&H60` | scan code ของคีย์บอร์ด | - |

พอร์ตอื่นทั้งหมดอ่านได้ 0 และ OUT ไปก็ไม่มีผล รวมถึง timer (`&H40`-`&H43`),
ลำโพง (`&H61`) และจอยสติก (`&H201`) `WAIT` จะเรียก INP ซ้ำ:
`WAIT &H3DA, 8` รอเฟรมถัดไป ส่วนพอร์ตอื่นคืนค่าทันที `STICK` คืน 128 และ
`STRIG` คืน 0 (ไม่มีจอยสติก)

## _FLOAT

`_FLOAT` เป็นเลขทศนิยม 80 บิตแบบ x87 extended ที่คำนวณด้วยซอฟต์แวร์ ได้ผล
ตรงกับหน่วย x87 ทุกบิต `EXP`, `LOG` และ `^` ที่เลขชี้กำลังไม่ใช่จำนวนเต็ม
ใช้หน่วย x87 บน x86/x86-64 ส่วน CPU อื่นใช้เวอร์ชันซอฟต์แวร์ ซึ่งได้ผลต่าง
จากหน่วย x87 ราว 3% ของ input และต่างไม่เกิน 1 หน่วยในตำแหน่งสุดท้าย (D-111)
โค้ดที่ใช้ `_FLOAT` ไม่ถูกคอมไพล์ด้วย JIT จึงช้ากว่าโค้ด SINGLE และ DOUBLE

## คำสั่งที่ยังไม่รองรับหรือทำงานต่างไป

การ build จะหยุดด้วย `QIR: unsupported: line N: ...` เมื่อเจอ:

- `LPRINT`, `ECHO`, `CALL INTERRUPTX`, `_GL` และ `SUB _GL` (D-14: ไม่มี
  OpenGL context)
- `RANDOMIZE` ที่ไม่มี seed (QBasic จะถามหา seed)
- `VARPTR$` ของสตริง
- `ON KEY(n) name` ที่ใช้ชื่อ SUB
- `DEF FnName ... END DEF` แบบหลายบรรทัด (แบบบรรทัดเดียว `DEF FnName(x) = นิพจน์` ใช้ได้)
- `_MEM` ของ array สตริงหรือของ STRING ความยาวไม่คงที่, `_MEMFILL` ที่ไม่มี
  `AS type`, `_MEMGET` ลงใน STRING ความยาวไม่คงที่

คอมไพล์ได้ แต่ทำงานต่างไป:

- `TIME$ = ...` ไม่ตั้งนาฬิกา
- `PLAY ON/OFF/STOP` และ `ON PLAY(n) GOSUB` คอมไพล์ได้ แต่ไม่เคยเกิด event
  PLAY (D-24)
- `CHAIN` ไม่ส่งตัวแปร COMMON ต่อ ส่วน `RUN file$` และ `CHAIN` จะรอให้อีก
  โปรแกรมทำงานจบ

## โปรแกรมที่จับเวลาด้วยการวนลูป

โปรแกรมเก่าบางตัววัดความเร็วเครื่องด้วยลูปเปล่า แล้วหน่วงเวลาด้วยการนับรอบลูป หรือคูณ
เวลารอด้วยความเร็วที่วัดได้ โปรแกรมเหล่านี้เขียนไว้สำหรับเครื่องที่ช้ากว่าราวพันเท่า จึงพัง
แบบเดียวกันทั้งใน QBasic บนเครื่องเร็วและใน QB64: ลูป 1000 รอบใช้เวลาจนวัดไม่ได้ (หารแล้ว
ผิดพลาดหรือได้ 0) และช่วงพักที่คูณด้วยจำนวนรอบอาจนานเป็นชั่วโมง โปรแกรมแบบนี้คอมไพล์
และรันได้ ให้แก้โค้ดหน่วงเวลาให้รอตามนาฬิกา เช่น
`t# = TIMER(.001): DO: LOOP UNTIL TIMER(.001) - t# >= .05`

## ข้อบกพร่องที่ยังไม่ได้แก้

| รหัส | ข้อบกพร่อง |
| --- | --- |
| L-01 | label ของ handler `ON ERROR` ที่อยู่หลัง SUB (หรือหลัง `$INCLUDE` ที่มี SUB) คอมไพล์ไม่ผ่าน |
| L-12 | `LINE INPUT #` กับไฟล์ BINARY ทิ้งบรรทัดสุดท้ายที่ยาว 1 ตัวอักษร |
| L-15 | `TIMER ON` หลัง `TIMER STOP` ทำ event ที่ค้างระหว่าง stop หาย |
| - | การปิดหน้าต่างของโปรแกรมที่อยู่ในลูป `SOUND` ใช้เวลาราว 2.6 วินาทีกว่าโปรแกรมจะจบ |
| - | โปรแกรมที่ใหญ่มากเริ่มทำงานช้า เพราะ JIT คอมไพล์ทั้งโปรแกรมตอนเริ่ม (16 วินาทีสำหรับ 10,800 บรรทัด) |

ยังไม่ได้ตรวจกับ runner QIR (พบใน runtime C++ เดิม): L-08 ประมาณ 1 ใน 300-400 ครั้งที่รัน โปรแกรมจบด้วย exit code `0xC0000409` และ L-10 หลัง `OPEN "COMn:..."` ครั้งแรก ชื่อ COM ครั้งต่อไปล้มเหลว
